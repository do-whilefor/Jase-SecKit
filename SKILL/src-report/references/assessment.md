# 漏洞筛选与 CVSS 3.1

在整理证据后、填写平台字段前读取。筛选规则来自用户提供的 `refer/过滤.txt`，是本技能的证据门槛，不是各 SRC 的官方拒收清单；下表已完整纳入规则，运行不依赖 `refer/`。CVSS 依据 [FIRST CVSS v3.1 规范](https://www.first.org/cvss/v3.1/specification-document)，只计算 Base，不计算 Temporal 或 Environmental。

## 先筛选证据

以下发现默认作为线索。只有用户提供的动态材料支持**安全边界失效、可稳定复现、实际影响**三项时，才按漏洞撰写；技能不执行 PoC 或主动补测。命中类别不等于无漏洞，未命中也不等于漏洞成立，不按名称或关键词自动丢弃材料。

| 编号 | 默认作为线索的发现 |
| --- | --- |
| F1 | CORS、安全响应头、版本、框架、普通报错、SSL/TLS 等配置或指纹信息。 |
| F2 | robots.txt、Sourcemap、JS、前端路由、接口路径、GraphQL/Swagger、注释、字段名或内部系统名等暴露面信息。 |
| F3 | 隐藏接口、状态码或前端限制绕过，但后端认证、对象归属、租户隔离和权限校验未失败。 |
| F4 | Self-XSS、仅影响本人非敏感资料、单独开放重定向、理论 Clickjacking 或低影响 CSRF。 |
| F5 | Rate Limit 缺失但未证明真实损害；上传成功但未证明可执行、触发危险解析、绑定高价值对象或绕过权限。 |
| F6 | 公开文件、URL、客户端 Key 或配置无敏感内容、有效权限、业务引用或边界失效。 |
| F7 | 少量测试数据、公开数据、本人数据或低敏数据，以及无法证明有效的 Token、JWT、密钥或签名参数。 |
| F8 | 扫描器、banner、CVE 指纹命中，或缺少完整请求、响应、状态结果和实际影响的发现。 |

逐项记录实际命中的规则及理由，不仅看漏洞标签。例如只有 CORS 响应头属于线索；若材料证明攻击者来源能读取受害者的非公开数据，且条件和复现过程完整，应根据该证据重新评估，不能仅因“CORS”排除。只见 HTTP 200、上传成功或“测试成功”的自述，不能替代实际边界失效证据。

三项依据引用 `case.json` 中已有论断 ID，论断继续引用原件编号和定位：

- `boundary`：说明原本不允许谁对什么对象做什么，以及材料显示如何越过该限制。跨账号仅是线索，还要有身份、归属与权限对照。
- `reproducibility`：材料中的触发前提、完整操作、请求/响应或状态变化及复现记录足以支持稳定复现；代码存在或单张成功截图不足以单独说明稳定性。
- `impact`：已观察到的非公开信息读取、未授权修改、服务影响等实际后果及范围，区分推测和事实，不用最坏假设补足影响。

`triage.status` 使用 pending（尚待评估）、lead（证据不足，仅为线索）、supported（三项均有材料支持）。缺口具体说明“缺什么、影响哪个判断、需提供哪类已有材料”，不把缺证据写成“无漏洞”或“误报”。保留原始材料；补证后重新评估，不能永久丢弃线索。

对于显式 pending/lead，或 supported 但依据校验未通过的案件，`report.md` 输出简短线索记录：评估理由、已观察内容、证据定位和补证项，不套用确认漏洞的标题、危害或评级。此时 `src_fields.json` 的 fields/groups 可为空。supported 才进入平台报告编写；CVSS 待评估不阻止交付有明确缺口的报告草稿。

## 再评估 CVSS

每项指标记录选择理由和支撑论断 ID；不能根据漏洞名、模板默认值或想要的严重性倒推向量。以下是选值要点，具体定义以 FIRST 规范为准：

| 指标 | 需要说明的依据 |
| --- | --- |
| AV | 攻击所需的网络、相邻、当地或物理接触条件；不是测试者当前所在位置。 |
| AC | 成功是否依赖攻击者控制之外的条件；不是编写 PoC 的难度。 |
| PR | 利用前攻击者需要的权限；不是利用后获得的权限。 |
| UI | 是否需要攻击者以外的用户参与。 |
| S | 受影响组件是否超出漏洞组件的安全权限范围；跨账号、跨子域或系统名称不同不自动等于 Changed。 |
| C | 对保密性的实际影响及限制。 |
| I | 对完整性的实际影响及限制。 |
| A | 对可用性的实际影响及限制；不得为评分执行破坏性验证。 |

未知不等于 N；例如 C/I/A:N 表示无相应影响，不能用来填补没有评估的信息。PR:N 和 UI:N 也须有依据。缺任一指标的依据时保留待评估和具体原因，不报告看似精确的正式分数，也不默认给三个 H。现有证据仅证明有限影响时，不能扩展成批量、全量或最高权限影响。

评分使用 `scripts/cvss31.py`，按规范重新计算，不信任手填分数。例如下列向量只是计算用例，不能套用于具体案件：

```text
python <skill>/scripts/cvss31.py "CVSS:3.1/AV:N/AC:L/PR:L/UI:N/S:U/C:L/I:N/A:N" --json
```

正常报告流程由检查器调用计算器，无需重复运行命令。只有筛选通过、完整向量及八项依据均通过引用校验，才在报告的“漏洞评估”中展示分数、向量与指标依据；这不是额外的 SRC 表单字段。CVSS 的 NONE/LOW/MEDIUM/HIGH/CRITICAL 与平台自评等级分别处理，不机械映射、不以 0 分判为误报，也不以高分确认漏洞或承诺平台收录。

程序只能验证结构、引用、声明和公式，无法确认实际漏洞、动态复现及指标选择是否正确。宿主仍须对照原件完成 `semantic_review`，并对新增评估文字执行内容及脱敏复核。
