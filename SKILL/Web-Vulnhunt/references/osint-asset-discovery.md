# OSINT & Asset-Discovery Playbook

22 techniques distilled from the AcmeAuth engagement. Each has: technique name, concrete example, tool/command, when to apply, gotchas.

**Cross-cutting caveat:** DNS conditions differ between environments. Sessions 1–5 (early) returned **RFC 2544 sinkhole addresses (`198.18.0.0/15`)** for *every* `*.cdn.acmeauth.example` / `*.acmeauth.example` query, including obviously-fabricated hostnames. Detection: resolve a guaranteed-fake hostname; if it returns `198.18.x.x` instead of NXDOMAIN, you are behind a benchmarking/sinkhole resolver. Workaround: pivot off CT logs rather than live DNS, and validate CT-discovered hostnames with live HTTP probing — sinkhole IPs return `000`/timeout on TCP connect, real hosts return HTTP. Run `scripts/sinkhole-detector.sh` first.

## Honesty notes (do NOT propagate uncorroborated intel)

During skill construction, several "remembered facts" turned out NOT to be in the source corpus. The skill deliberately excludes:

1. **Greenhouse ATS API (`boards-api.greenhouse.io/v1/boards/<vendor>`)** — not referenced. Stack was confirmed via runtime fingerprints (UA, stack traces, error templates), not job postings. The technique is valid in principle but was not part of this engagement.
2. **Postman workspace slug `acmeauthcorp/acmeauth-s-public-workspace`** — actual workspace was `apidocs.<domain>` (CNAME `phs.getpostman.com`, collection `20355028`). Always derive the workspace from CNAME, not from a guessed slug.
3. **`controlCenterAdmin` as a "pseudo-appId"** — it is just the rpAppId used for CC-admin login, referenced in F4/F5/F7/F9 reports. Not a special "pseudo" construct.
4. **"30-day sliding token TTL"** — the documented OAuth TTL is `oauthBearerTokenTTLSecs: 600` = 10 minutes (Bearer). The 89-day figure is for WORKSTATION Bearer; the unexpiring figure is for install tokens. Don't conflate.
5. **WSO2 / Bravura Security / SecureAuth integration OSINT** — not present in corpus. Only PingOne DaVinci (`ping_davinci_cc` realm) and `BEYOND_TRUST` are documented as AcmeAuth SSO integrations.
6. **`acmeauth.example/customers` case-study page cross-referencing with <customer>/<customer>** — not a documented step. <customer> + <customer> appear only in APK marketing strings. <customer> does not appear at all. Customer recon was done via CT-log `vault-<customer>` prefixes.
7. **GitHub code-dork queries `filename:application.yml`, `"acmeauth-session-token"`, `"cc/basic/token"`** — not documented as run. The only documented GitHub searches were org/account enumeration, the `<vendor-employee>/public` personal-repo discovery, and a Session-3 Bing search for `"com.acmeauth.server.commons"` / `"acmeauth-server" signingKey` / `"ENABLE_CUSTOM_EVENT_MGMT"` (all negative).

Apply the same honesty discipline to your own future engagements: prefer runtime evidence over OSINT inference; document what you actually ran, not what you "think you remember running."
